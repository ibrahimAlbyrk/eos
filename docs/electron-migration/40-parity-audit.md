# 40 — Electron port parity + performance audit (M7)

Independent A/B parity + performance audit of the packaged Electron port
(`app-electron/`) vs the installed native `Eos.app`, against the same running
daemon. This auditor did **not** build the port — findings below come from real
captures/measurements and from running the port's own verification code paths,
not from restating the builder's per-milestone claims.

- **Verdict: conditional GO** — ship-ready on pixel/behavior parity; blocked on
  two non-cosmetic cutover items (M6 signing/notarization; the daemon-spawn fd
  bump for a standalone shell). See §5.
- Date: 2026-08-29. Auditor: `parity-auditor` worker.
- Harness under test: `out/Eos Electron-darwin-universal/Eos Electron.app`
  (`com.eos.electron.dev`, adhoc-signed universal build), packaged M6 output.
- Reference: `/Applications/Eos.app` (native Swift shell, pid 2457).
- Daemon: `127.0.0.1:7400`, pid 2276, healthy, `fds 3112/61440`. Both shells
  reuse it; neither was spawned/restarted during the audit.
- Captures: `app-electron/verify/audit/` (this audit) + `app-electron/verify/`
  (builder's per-milestone + the M3/M4 frames re-generated by re-running the
  harnesses during this audit).

## Method & honesty notes

- **Capture technique.** The operator's machine was in active use during the
  audit (FaceTime, a fullscreen video player on another Space). Screen-region
  capture proved unreliable and would have captured the operator's private
  content, so all window captures use `screencapture -o -l<windowId>` (per-window
  backing-store capture), which grabs only the target window regardless of
  z-order/focus and never the operator's other content. Window IDs came from a
  small Swift `CGWindowListCopyWindowInfo` helper (no PyObjC in the env).
- **Pixel diffs** use ImageMagick 7 `compare -metric AE`/`RMSE` with fuzz
  tolerances; per-region masks measured with `-fx` color isolation + `-trim`.
- **What could NOT be driven live**, and why: interactive modal targets and some
  UI gestures were unreliable to click on the focus-contested live machine
  (clicks intermittently consumed by focus changes; a stray double-click even
  put a worker row into rename mode — cancelled with no change). Rather than
  risk mis-clicks in the operator's live workspace (Commit/Publish/PR buttons),
  the flagged interactions (Finder drag-drop, terminal clipboard, undo/redo,
  external-link, notification-click) were verified by **(a) source inspection of
  both bridge ends and (b) re-running the port's own M2/M3/M4 verification
  harnesses**, which execute the real bridge/tray/notification code against the
  live daemon and print machine-checkable verdicts. Items so verified are marked
  `PASS (wiring+harness)` rather than `PASS (live gesture)` — see §2. This is an
  honest distinction: the code paths are proven present and functional; a
  physical Finder-drag / terminal-selection gesture was not performed by a human.

## 1. Visual A/B across the matrix

The port re-hosts the **same** `app/ui/dist` bundle both shells consume, so web
content is identical by construction; the parity question is whether the Electron
**shell chrome** reproduces the AppKit chrome pixel-for-pixel, and whether
cross-engine (WebKit→Chromium) rendering stays within the §D9/R13 budget.

Both windows forced to identical bounds (1280×820) on the same display, same
daemon data. Display is 1×, so captures are 1280×820 logical px.

| Green | 14×14 @ +65,+8 | 14×14 @ +65,+8 |

Centers land on the same pixel (23-px spacing, both). Region AE = 120/6000 px

`+3pt`-nudged spot. → **0px geometry delta.** (`tl-compare-active.png`)

**Traffic lights (inactive/unfocused).** Both render the greyed cluster; cluster
bbox identical (127×22 @ +0). Region AE = 202/6000 (3.4%), edge AA only.
(`tl-compare-inactive.png`)

sub-50%-threshold AA. → **radius curve identical, 0px at threshold.**

**Background color — exact.** Dark base sampled `srgba(26,26,26)` = `#1a1a1a` in
titlebar, content-top, and mid-content, **both apps**. Light base `srgb(246,241,230)`
= `#f6f1e6` (Electron; matches `config.ts` `LIGHT_BG` and the shell's repaint
target). → **exact.**

## 3. Performance vs native

Measured with `ps`/`top` on the confirmed process trees (native WKWebView spawns
separate WebKit XPC processes — pids 2458/2464/2472 all started at Eos.app's
launch instant 07:51:47 — which must be included for a fair comparison; the Swift
shell process alone is only ~43 MB and badly understates native).

| Metric | Native `Eos.app` | Electron port | Delta / note |
|---|---|---|---|
| **RSS, full process tree** | **189.8 MB** (shell 43.1 + WebContent 114.9 + GPU 21.5 + Net 9.8) | **288 MB** (main + renderer + GPU + net-utility) | **+98 MB** fair full-tree |
| RSS vs shell-only ("thin wrapper" framing) | 43 MB | 288 MB | +245 MB — matches doc 30 §3's 150–300 MB estimate, but understates native |
| Process count | 4 | 4 | equal |
| **CPU under live SSE** (daemon had many active workers repainting) | ~44–48% (tree) | ~34–40% (tree) | Electron **not worse** — comparable / slightly lower. NB: not true-idle; both would be far lower with no active workers |
| **Cold launch → first window** | not re-measured (see note) | **0.73–1.01 s** (3 clean runs, full teardown) | Electron ~1 s incl. daemon health-probe (probe wins instantly, daemon already up) |
| **On-disk** | **28 MB** | **520 MB** universal (~319 MB arm64-only per README) | ~11–18× larger — bundled Chromium vs system WebKit reuse |
| Daemon fds | — | 3112 / 61440 | running daemon already carries the fd bump |

Notes:
- **Native cold-launch not re-measured**: doing so requires quitting/relaunching
  the operator's live shell mid-session; declined to avoid disruption. Native
  reuses the always-resident system WebKit framework, so its cold start is
  dominated by the same daemon health-probe both shells wait on, plus a
  near-instant WKWebView init — expected ≤ Electron's ~1 s. Stated as reasoned
  expectation, **not** a measured number.
- **RSS is soft**: WebKit XPC processes share framework pages; treat ±20 MB as
  noise. The +98 MB full-tree overhead is the honest headline and is at the
  **low end / below** doc 30's 150–300 MB estimate (R11) because native's real
  footprint includes a heavy 115 MB WebContent process, not just the thin shell.
- **Disk is the largest regression** and is real: 520 MB (universal) vs 28 MB.
  An arm64-only cutover build (~319 MB) narrows it but it stays ~11×.

### fd-limit / daemon-spawn (explicit call-out)

The `ulimit`/fd-bump wrapper (doc 10 §f12, "non-negotiable") is **intentionally
NOT implemented** — `daemon.ts` only *probes* the already-running daemon and never
spawns one, so the port inherits the bump the native app/CLI already applied (the
live daemon shows `limit 61440`). This is correct for the current reuse model.
**Production-cutover requirement:** a standalone Electron shell that spawns its own
daemon MUST replicate the fd bump before that daemon serves load, or it will
mis-read port/fd exhaustion as a dead daemon (the exact bug the unix-socket
control plane was added to avoid). Flagged, not a defect of the current port.

## 5. Regressions, ranked → GO / NO-GO

### Ranked gaps

1. **[BLOCKER] M6 signing + notarization incomplete.** `codesign` = `adhoc,
   linker-signed`, `TeamIdentifier=not set`; `spctl -a` = **rejected ("no usable
   signature")**; `stapler validate` = **no ticket**. Runs locally; **cannot be
   distributed / will trip Gatekeeper**. Needs a Developer ID Application cert +
   notarization (wiring exists, credentials/network submit do not). (GAP8)
2. **[BLOCKER for standalone] Daemon-spawn fd bump absent.** Fine while reusing a
   running daemon; mandatory before a self-spawning production shell ships (§4).
3. **[ACCEPTED] Disk footprint 520 MB / ~319 MB arm64 vs 28 MB native.** Inherent
   Chromium cost; ship arm64-only to reduce. Not a blocker.
4. **[ACCEPTED] Memory +98 MB full-tree.** Within/below estimate (R11).
5. **[ACCEPTED, cosmetic] Splash Liquid-Glass delta on macOS 26** (Q3). Seconds,
   splash-only.
6. **[ACCEPTED, one-time] localStorage ephemeral-pref reset at cutover** (R12).
   Release-note it.
7. **[MINOR-UNVERIFIED] R4 double-click-zoom pref**, **R14 7401-iframe renderer
   footprint**, **Q1 fullscreen reveal-strip TL pixels**, and the five
   wiring+harness-but-not-live-gesture interactions (§2). No evidence of breakage;
   each is a cheap follow-up confirmation, not a known regression.

### Pixel-perfect design rule (the #1 bar): **MET.**
Chrome (traffic lights, corner radius, background color) is **0px / exact** in
both focus states; interior differs only by sub-pixel cross-engine glyph AA
(layout + color identical), within the §D9/R13 budget. No visible chrome
difference found at any zoom.

### Verdict: **CONDITIONAL GO**

The port is **parity-complete and behavior-complete** for a cutover on this
machine: it renders the identical UI against the live daemon, chrome is
pixel-perfect, every §E capability is wired and (where safely drivable) verified,
performance is acceptable, and it survives kill/relaunch cleanly. **Go** for
internal/dev use now.

**Conditions that must be met before a production cutover** (replacing
`/Applications/Eos.app`):
1. **M6 signing + notarization** with a Developer ID Application cert (BLOCKER 1).
2. **Daemon-spawn fd bump** implemented + verified IF the production shell spawns
   its own daemon (BLOCKER 2). If the production model keeps reusing an
   externally-managed daemon, this is waived.
3. **Optional pre-cutover confirmations** (not blockers): one live pass of the
   five wiring-verified interactions (Finder-drag, terminal copy/paste, composer
   undo/redo, external-link, notification-click) on an idle machine; R14 memory
   with a 7401 browser panel open; R4 double-click-zoom; ship arm64-only to trim
   disk. Release-note the one-time localStorage reset (R12).

No pixel deltas gate the cutover. The two blockers are packaging/ops items, not
parity defects.
